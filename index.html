🔌 OCPP

Open Charge Point Protocol — комуникация между физическата зарядна станция и CSMS/backend.

EV Charger ↔ OCPP ↔ AMPECO / CSMS Backend
  • Статус на charger
  • Start/stop на сесии
  • Авторизация
  • Транзакции
  • MeterValues
  • Remote commands и диагностика

🔗 OCPI

Open Charge Point Interface — обмен между различни участници/платформи в charging екосистемата.

CPO ↔ OCPI ↔ eMSP / Roaming Partner
  • Локации и зарядни точки
  • Тарифи
  • Charging sessions
  • CDR — Charge Detail Records
  • Tokens/authorization
  • Roaming

🔗 OCPP vs OCPI — основна разлика

OCPP = Зарядна станция ↔ Backend
OCPI = Backend/оператор ↔ Друг backend/оператор

🔋 Други стандарти

  • OpenADR — demand response / управление на енергийното натоварване.

OCPP Handbook 2026 — condensed

⚡ OCPP в 20 секунди

OCPP е отвореният, manufacturer-neutral протокол, чрез който зарядната станция комуникира с CSMS/backend като AMPECO.
EV → Charging Station ↔ OCPP ↔ CSMS / AMPECO Backend

Защо съществува? Interoperability и по-малък vendor lock-in: операторът може да използва зарядни от различни производители с централен backend.

🧠 Какво трябва да запомня

  • Charge Point / Charging Station = client
  • CSMS / Central System = server/backend
  • OCPP пренася status, authorization, transactions, MeterValues, remote commands, firmware/diagnostics и smart charging.
  • OCPP 1.6 остава най-разпространената версия през 2026.
  • 2.0.1 е голям redesign с device management, по-добри transactions/security и ISO 15118.
  • 2.1 е най-новото поколение; добавя backward compatibility в 2.x линията и V2X възможности.

🎯 Основни ползи

  • Interoperability: различни charger manufacturers ↔ различни backends.
  • Remote management: monitor, start/stop, configure, diagnose.
  • По-добро driver experience: authorization, billing, payments.
  • По-ниски разходи: по-малко ръчна намеса, повече operational data.
  • Future-proofing: отворен стандарт, който се развива.
  • Smart charging: динамичен контрол на power/current според grid, availability и price.

🧩 OCPP речник

  • Profile: група функционалности/messages (особено при 1.6).
  • Message: единица данни между charger и CSMS.
  • Data type: string, integer, boolean, date-time, enum и др.
  • Configuration key: настройка, която влияе на charger поведението.
  • Use case: сценарий като start/stop/remote start transaction.
  • Test case: проверка дали implementation-ът се държи според стандарта.
  • ChargingProfile: правила за power/current във времето; съдържа ChargingSchedule.

Support mindset: намери къде по веригата очакваното message/data липсва, закъснява или е невалидно.

📟 Metering / MeterValues

  • Charger-ът изпраща измервания към CSMS.
  • Може да са periodic samples или clock-aligned intervals.
  • Данните могат да включват energy, voltage/current и други измервания.
  • Използват се за monitoring, charging session data, billing и grid/load management.

Support example: „Сесията показва 0 kWh“ → провери дали charger-ът е изпратил очакваните metering data/MeterValues и как backend-ът ги е обработил.

🎛️ Какво правят важните blocks?

  • Provisioning: station registration + basic configuration.
  • Authorization: кой има право да зарежда.
  • Transactions: start/stop и transaction lifecycle.
  • Remote Control: remote transaction, unlock connector, remote trigger.
  • Availability: status notifications.
  • Tariff & Cost: price before/during/after charging.
  • Diagnostics: request/upload diagnostics + monitoring data.
  • Data Transfer: custom/vendor extensions.

⚙️ Smart Charging

  • CSMS влияе на charging current/power.
  • Charging Profiles задават power/current limits във времето.
  • Може да работи на EVSE, station или site/group level.
  • Цел: load balancing, grid protection, оптимизация на energy cost.

🚀 2.0.1 — какво е голямото

  • Device Management: по-дълбока видимост и управление на сложни multi-vendor networks.
  • Transactions: по-унифицирано reporting.
  • Security: TLS, certificates, secure firmware, security events/logging.
  • Smart Charging: EV може да комуникира необходимата energy.
  • ISO 15118: Plug & Charge + по-богата EV↔EVSE комуникация.
  • Display messages: tariff/running/final cost и driver-facing messaging.

🔌 Съседни протоколи

  • ISO 15118: EV ↔ charger; Plug & Charge и V2G/V2X capabilities.
  • OpenADR: utility/grid → demand-response signals → CSMS може да коригира charging behavior.
  • OCPI: backend/operator ↔ друг backend/operator; roaming ecosystem.
  • OSCP: charging management systems ↔ smart charging/grid services; по-високо ниво от charger operations.

🛡️ Security

  • 1.6 може да използва TLS, но често се допълва с VPN/private networks/IPsec.
  • 2.0.1 добавя по-цялостен security model: certificates, secure firmware, security logs/events и TLS profiles.
  • Certification/testing има значение: „поддържа OCPP“ не означава автоматично качествен implementation.

🧪 Hardware interoperability

  • Качеството на charger firmware/OCPP implementation директно влияе на reliability.
  • Лош implementation → partial functionality, weird edge cases, unreliable communication.
  • Тестват се remote start/stop, firmware updates, smart charging и други core/advanced scenarios.
  • AMPECO работи с hardware manufacturers за подобряване на interoperability.

🌍 Regulations — защо OCPP помага

  • UK smart charging: off-peak behavior, randomized delays, user override, secure communication; OCPP може да подпомогне compliance.
  • German Eichrecht: точен kWh metering и проверими billing data; OCPP пренася metered data към CSMS.

🧪 Testing & evolution

  • OCTT2: compliance testing за OCPP 2.0.1.
  • Certification: доказва conformity към официалните specifications.
  • Plugfests: vendors тестват interoperability помежду си.
  • Protocol-ът се развива чрез industry working groups.

⚠️ Implementation reality

  • OCPP е труден за правилно implement-ване.
  • Документацията сама по себе си дава protocol basics, не цял charging business.
  • Различните versions не са автоматично взаимозаменяеми; migration може да изисква firmware/hardware/software changes.
  • Business cases, local regulation и hardware quirks правят реалната среда по-сложна от спецификацията.

🔧 Support Troubleshooting

Когато нещо се счупи, мисли по веригата:
Charger state → Connectivity → OCPP message → Payload/data → CSMS processing → Business logic
  • Charger offline? connectivity, WebSocket/TLS, configuration, station status.
  • Не стартира? authorization, transaction messages, connector availability.
  • 0 kWh / грешна energy? MeterValues/metering + backend processing.
  • Remote command fails? station connectivity + supported profile/functionality + response.
  • Само конкретен model прави проблем? подозирай charger-specific OCPP implementation/firmware.

📌 Key Technical Concepts

  • OCPP: „Стандартизира комуникацията между charger-а и CSMS/backend-а.“
  • Главната полза: „Interoperability и избягване на vendor lock-in.“
  • 1.6 vs 2.0.1: „2.0.1 е redesign с по-добър device management, transaction model, security и ISO 15118 support.“
  • MeterValues: „Metering data от charging station към backend по време/около charging session.“
  • Support: „Бих проверил expected message flow и бих локализирал дали проблемът е connectivity, charger implementation, payload/configuration или backend processing.“

OCPP technical overview

⚡ OCPP in 20 seconds

OCPP is an open protocol allowing EV charging stations to communicate with central management software regardless of charger manufacturer.
EV → Charging station ↔ OCPP ↔ CSMS / AMPECO

Its core value is interoperability, remote management and reduced vendor lock-in.

🧠 Key facts

  • Charge point: Usually the WebSocket client.
  • CSMS: The backend/server.
  • Exchanges status, authorization, transactions, meter readings, remote commands and diagnostics.
  • OCPP 1.6J: Widely deployed JSON/WebSocket version.
  • OCPP 2.0.1: Revised transaction model, device management and security.
  • OCPP 2.1: Further capabilities including V2X-related functionality.

🎯 Benefits

  • Interoperability between compatible hardware and software.
  • Remote monitoring, configuration and troubleshooting.
  • Session authorization and metering for billing.
  • Smart charging and energy management.

📡 JSON/WebSocket vs SOAP/XML

JSON / WebSocketSOAP / XML
Compact messages and persistent two-way connection.XML-based messaging, typically with more network complexity.
Common for OCPP 1.6J and 2.x.Supported by older OCPP implementations.
Check WebSocket connectivity, TLS and payloads.Check HTTP endpoints, firewall and XML messages.

🧩 OCPP concepts

  • Message: Protocol request, response or event.
  • Profile: Group of related functions (especially in OCPP 1.6).
  • Configuration key: Setting that changes charger behavior.
  • ChargingProfile: Power/current limits over time.
  • Measurand: Type of metered value, such as energy or voltage.
  • Test case: Validation of expected behavior.

🔁 Typical session flow (OCPP 1.6)

BootNotification → Heartbeat / StatusNotification → Authorize → StartTransaction → MeterValues → StopTransaction

Actual messages and order depend on the charging scenario and charger implementation.

📊 Metering and transactions

  • MeterValues: Reports measured energy, power, voltage or current in OCPP 1.6.
  • Transaction ID: Links messages to the charging transaction.
  • kW: Power, or charging rate.
  • kWh: Energy delivered over time.
  • TransactionEvent: Main transaction lifecycle message in OCPP 2.x.

🔐 Security and connectivity

  • Validate charger identity, endpoint URL and credentials.
  • Check TLS certificates, WebSocket handshake and connectivity.
  • Inspect timestamps, correlation IDs and request/response payloads.
  • Confirm supported OCPP version and security profile.

⚡ Smart charging

  • Control charging limits according to grid capacity, load or pricing.
  • Charging profiles can set current/power constraints.
  • Load balancing shares limited electrical capacity across chargers.

🕰️ Protocol versions

  • 1.5: Legacy generation.
  • 1.6: Widely adopted; JSON/WebSocket variant and smart charging.
  • 2.0: Major redesign; not backward-compatible with 1.6.
  • 2.0.1: Improved device management, transaction model and security.
  • 2.1: Extends the 2.x generation, including V2X capabilities.

🧪 Interoperability and testing

  • Certification and compliance tests assess protocol behavior.
  • Plugfests allow manufacturers to test compatibility.
  • Real-world hardware and firmware implementations may vary.

🔧 Support troubleshooting

Follow the communication chain to isolate the fault.
Charger state → Connectivity → OCPP message → Payload → Backend processing → Business logic
  • Charger offline: Network, TLS, WebSocket, endpoint, heartbeat.
  • Session won't start: Authorization, connector availability, transaction flow.
  • 0 kWh: MeterValues, units, timestamps, transaction linkage, backend ingestion.
  • Remote command fails: Connectivity, command support and response.
  • Only one charger model fails: Firmware or manufacturer-specific implementation.

📌 Key technical concepts

  • OCPP standardizes charger-to-backend communication.
  • OCPP and OCPI solve different interoperability problems.
  • Investigate the expected message flow before assigning fault.
  • Different OCPP versions have different transaction models.
